# Daybook (dunnit) — FRD v1 (Functional Requirements)

Status: **first-pass FRD**, derived from `PRD-DRAFT-2026-08-28.md` v3
(fully resolved). Every surviving PRD item becomes one `FR-###` entry
here, each with a concrete acceptance criteria list — the same shape
`eca__task` items use (subject + description + acceptance criteria),
so this doc can be loaded 1:1 into a live task list later without
re-deriving anything.

This is everything from the PRD (per your "2. Everything in FRD"
instruction) — not pre-trimmed. Ordering below is a *proposed*
sequence, not a mandate; see "How ordering works" below for the
reasoning, and feel free to reshuffle before we load it as real tasks.

## How I ordered this (and how `eca__task` ordering works, briefly)

Two separate things determine "what to do next":

1. **Dependencies** (hard ordering) — some items literally can't be
   built before another exists. E.g. "Daybook shows open TODOs" (FR-06)
   needs the `TODO`/`GOAL` category split finalized (FR-02, already
   done in the PRD) and arguably benefits from category-legend/help
   text existing first, but doesn't *require* it. Where a real
   dependency exists, I've noted it as "Depends on: FR-##" and would
   set `blocked_by` on that task in `eca__task` — the tool then
   literally refuses to `start` a blocked task, so dependency order is
   partly enforced automatically, not just documentation.
2. **Priority/sequencing preference** (soft ordering) — everything
   else is a judgment call about value-vs-effort and what unblocks the
   most other value fastest. `eca__task` doesn't have its own opinion
   on this — it's just a tracker (statuses: pending → in_progress →
   done, plus `priority: high/medium/low` as a label you can sort by
   yourself). **We** decide order; the tool just remembers/enforces
   it once decided. Nothing algorithmic picks order for you.

My proposed heuristic for the phases below:
- **Phase 0**: real bugs in the shipped app — always goes first,
  independent of everything else, cheap and high-value.
- **Phase 1**: small, high-value, low-dependency items — mostly config/
  data-model changes (category additions, nudge-interval rename) that
  everything else in later phases assumes exist.
- **Phase 2**: the `TODO`/`GOAL` Daybook-list feature and its close
  cousins (carry-forward, undo/edit) — the biggest *concrete* new-
  feature ask from this round, and structurally similar work (all
  touch the Daybook UI + ledger read/write).
- **Phase 3**: the multi-screen sequences (SOD, SOM, meeting agenda
  view, mini-calendar) — bigger, each is really a mini-project, and
  several *do* depend on Phase 1/2 primitives (e.g. SOM's "prompt for
  IMPACT/MILESTONE" wants those categories to exist and have help text
  first).
- **Phase 4**: reporting/output and review/reflection features —
  mostly extensions of the existing Summarize pipeline; naturally
  later since they're additive/non-blocking for anything else.
- **Phase 5**: everything explicitly speculative, low-priority, or
  with real unresolved sub-decisions (streaks, AI-features-TBD, global
  hotkey, product rename) — not scheduled, listed for completeness
  per your "everything in FRD" instruction.

You don't have to accept this phase order — it's one reasonable
reading. Once you've reacted, I'll load the agreed set into
`eca__task` and we start executing top-down, one phase at a time,
re-checking priority as real work surfaces surprises (which it always
does).

## Phase 0 — Bugs (do first, no dependencies)

### FR-01: Suppress nudge if already logged this interval
**Description:** The periodic capture nudge currently fires on
schedule even if the user already logged an entry within the current
interval window. It should skip firing if an entry has already been
recorded since the last nudge fired (or since the start of the current
interval, whichever is the simpler correct check).
**Acceptance criteria:**
- Log an entry manually shortly before the next scheduled nudge time;
  confirm the nudge does *not* pop up at its scheduled time.
- If no entry was logged in the window, the nudge still fires as
  before (no regression).
- Behavior documented in code comments near the scheduler logic.

### FR-02: Fix Cmd+W / Ctrl+W not working from text-entry focus
**Description:** The hide-window shortcut doesn't fire when focus is
inside a text-entry box (the common case, since that's usually where
focus sits when Daybook is open). Needs investigation into Fyne's
focus/shortcut-dispatch interaction with text widgets and a fix.
**Acceptance criteria:**
- With cursor/focus inside the main text-entry field, Cmd+W (macOS) or
  Ctrl+W (other platforms) hides the window, same as when focus is
  elsewhere in the window.
- No regression to existing behavior when focus is *not* in a text
  field.

## Phase 1 — Small, low-dependency foundational changes

### FR-03: Add new categories to category enum/list
**Description:** Add `SOMEDAY`, `WAITING` (replacing/merging old
`BLOCKER`/`BLOCKED` concept), `FIXME`, `OPTIMIZE`, `QUESTION`,
`KUDOS`, `RISK` to wherever categories are defined (currently
hardcoded in `ui.go` per AGENTS.md). Revive `TODO` as an actively
encouraged category (already technically usable as free-text, but
should get a first-class button/label like other categories) and
`WAITING` covers the old `BLOCKER` real-world usage.
**Acceptance criteria:**
- All categories above appear as selectable options in Daybook's
  category picker, each with the emoji-label style already used for
  existing categories (pick reasonable new emoji for each).
- A logged entry using each new category writes the expected
  `[HH:MM] CATEGORY text #tag` line to today's ledger.
- `go vet` / `make build` clean; category list in code kept in one
  place (avoid duplicating the list across files) to ease future
  changes.
**Depends on:** none (foundational).

### FR-04: Nudge interval — "every N minutes" instead of fixed hourly
**Description:** Replace `hourly_minute` (minute-of-hour) config
concept with a genuine interval-based scheduler: `nudge_interval_minutes`
(e.g. 30/45/60/90), optionally with an anchor/offset if still wanted.
Update `Config` struct, `config.toml` defaults, Settings form, and
`sched.go`'s cron logic.
**Acceptance criteria:**
- `config.toml` has a new `nudge_interval_minutes` key (with a
  reasonable default, e.g. 60) replacing `hourly_minute`.
- Settings screen lets the user edit this value and it persists.
- Scheduler fires at the configured interval, not hardcoded to
  once-per-hour-at-a-fixed-minute.
- Existing configs without the new key still load without crashing
  (fallback to default).
**Depends on:** none, but touches the same scheduler file as FR-01, so
worth doing them in the same sitting to avoid merge friction with
yourself.

### FR-05: Drop `MTG`, consolidate to `MEETING` only
**Description:** Remove `MTG` as a distinct category if it currently
exists as a selectable option; ensure only `MEETING` is offered going
forward. (Historical `MTG` lines in old ledgers are left as-is — no
data migration needed, this is forward-only.)
**Acceptance criteria:**
- `MTG` no longer appears as a category option in Daybook.
- `MEETING` still works exactly as before.
**Depends on:** none.

### FR-06: In-app Category Legend (help text)
**Description:** Surface the intended-use text for every category
(from the PRD's §12 table, now the canonical source) directly in the
app — either as hover tooltips on category buttons/labels, or a static
"Category Legend" screen reachable from the tray menu, whichever is
cheaper to build in Fyne (spike hover tooltips briefly first; fall
back to a static screen if fiddly).
**Acceptance criteria:**
- Every category (old and new from FR-03) has a one-line description
  visible in-app, without needing to consult README/AGENTS.md.
- Legend text lives in exactly one place in the codebase (e.g. a
  `categoryHelp map[string]string` or similar), referenced by both the
  tooltip/legend UI and (ideally) generatable into docs, so text can't
  drift between app and documentation.
**Depends on:** FR-03 (needs the final category list to write legend
text for).

## Phase 2 — TODO/GOAL workflow in Daybook

### FR-07: Daybook shows open TODOs with one-click convert-to-DONE
**Description:** Daybook's main nudge window displays currently-open
`TODO` lines (parsed from today's, or recent, ledger) as a list, each
with a simple action (button/checkbox) that logs a new `DONE` entry
referencing/rephrasing the `TODO` text. The original `TODO` line is
left untouched in the ledger (append-only design) — the new `DONE`
line is the record of completion.
**Acceptance criteria:**
- Open a `TODO` via manual entry; next time Daybook nudge appears (or
  is opened from tray), that `TODO` is visible in a list.
- Clicking the convert action appends a `DONE [HH:MM] <text> (via
  TODO)` (exact phrasing TBD, keep simple) line to today's ledger.
- Converted items no longer appear in the "open" list on subsequent
  nudges (simplest implementation: track "already converted" by
  scanning for a corresponding DONE reference, or maintain a small
  local marker — pick whichever is simplest to keep append-only).
- `GOAL` lines shown in the same list, less prominently/frequently
  (e.g. only shown once a day or in a separate section), with the same
  convert action.
**Depends on:** FR-03 (TODO as first-class category).

> **Open design question (added 2026-08-28, post-implementation):**
> Unconstrained TODO creation could lead to an ever-growing,
> unmanageable Upcoming list -- nothing currently stops someone from
> logging dozens of TODOs a day. The "Stall" button (marks an item
> SOMEDAY instead of DONE, removing it from Upcoming) is a partial
> mitigation -- it gives an easy way to triage/shrink the list -- but
> doesn't address the root cause of over-creation. Worth revisiting
> once real usage data exists: possible directions include a soft cap/
> warning when too many TODOs are open at once, a periodic forced
> triage prompt, or just trusting the user's judgment and treating
> this as a non-issue. No decision made yet -- flagging for future
> thought, not blocking any current FR.

### FR-08: Undo/edit last entry from tray
**Description:** Add a tray menu action to undo or edit the most
recently logged ledger line without opening `$EDITOR`/raw file.
**Acceptance criteria:**
- Tray menu has an "Undo last entry" (or "Edit last entry") action.
- Undo removes the last line from today's ledger file; edit opens a
  small in-app text field pre-filled with the last line's text,
  saving back over that line on confirm.
- Works correctly even if the ledger file was manually edited since
  the last app-driven write (i.e. always operates on the literal last
  line of the file, not a cached value).
**Depends on:** none, but naturally pairs with FR-07's UI work.

### FR-09: Carry-forward of unconverted TODOs
**Description:** At end of day (or as part of EOD flow, FR-13), any
`TODO` lines not converted to `DONE` are optionally re-listed into
tomorrow's ledger as fresh `TODO` lines (plain re-listing, no state
tracking beyond "was it converted or not," reusing FR-07's completion
check).
**Acceptance criteria:**
- Leave a `TODO` unconverted through EOD; confirm it (or an equivalent
  re-listed line) appears in tomorrow's ledger as a `TODO`.
- Converted `TODO`s are *not* carried forward.
- User can decline/skip carry-forward for a given item (not forced).
**Depends on:** FR-07 (needs the open/converted tracking logic), FR-13
(EOD is likely where this triggers).

### FR-10: Tag autocomplete from ledger history
**Description:** When typing a `#tag` in any entry field, suggest
previously-used tags (scanned from historical ledger files under
`DUNNIT_DIR`) rather than requiring exact retyping.
**Acceptance criteria:**
- Typing `#` (or a few characters after it) in an entry field shows a
  dropdown/suggestion list of matching historical tags.
- Selecting a suggestion inserts it cleanly into the entry text.
- Reasonable performance even with a large history (don't rescan all
  files on every keystroke — cache tag list at startup or on-demand,
  refresh periodically).
**Depends on:** none.

## Phase 3 — Multi-screen sequences and meeting/agenda features

### FR-11: "Meeting prep" button + tag-scoped MEETING capture
**Description:** Add a "Meeting prep" action (button/tray item) that
prompts for a tag (e.g. `#jeff`, `#boss`) and logs a `MEETING` entry
under that tag immediately.
**Acceptance criteria:**
- Action is reachable from tray and/or Daybook.
- Prompts for tag text, then free-text note; writes a `MEETING` line
  with that tag to today's ledger.
**Depends on:** none directly, but pairs with FR-12 to be useful.

> **Re-scoped (2026-08-29, post-implementation):** the original spec
> above undersold the actual intent -- the dialog should also show the
> last ~8 entries (any category, not just MEETING) matching the given
> tag, pulled from ledger history within a user-selected lookback
> window (dropdown: 1/2/3/4/12 weeks, default 2), so the user can see
> what's accumulated under that tag over time. This pulled history is
> shown in an editable text box for scratch/annotation purposes only
> -- editing it never writes back to the original ledger files
> (append-only design preserved). The original capture-a-new-note
> behavior is kept as a separate "Save Note" action alongside the
> history view, not replaced by it. Implemented this way in
> `meetingprep.go` (see `pullTaggedEntries`). The "2 weeks" default
> lookback is currently just a fixed default, not yet wired to a
> per-tag meeting-frequency setting -- that's a future refinement,
> once a settings-based meeting-frequency feature exists (see FR-15/16
> mini-calendar notes below) to derive a smarter default from.

### FR-12: Agenda view — pull accumulated MEETING notes by tag
**Description:** Given a tag, show all `MEETING`-tagged lines
accumulated since the agenda for that tag was last pulled/viewed,
formatted as a ready list — the "ready-made agenda" payoff for FR-11's
capture mechanism.

> **Note (2026-08-29):** FR-11's re-scoped implementation above now
> already covers most of this (pulling tagged history on demand,
> scoped by tag + lookback window). What's still missing relative to
> this FR's original spec: (a) filtering to MEETING category
> specifically rather than any category, and (b) the "last pulled"
> marker/only-show-new-since-last-time behavior. Revisit whether a
> separate FR-12 implementation is still needed, or whether it's
> better folded into further refinement of showMeetingPrepDialog,
> when this is picked up next.
**Acceptance criteria:**
- User can select/type a tag and see all matching `MEETING` lines
  across relevant ledger files (at least today + recent days; date
  range handling can start simple, e.g. last 30 days).
- A "last pulled" marker per tag is stored (simplest: a small file or
  entry in config under `DUNNIT_DIR`) so a repeat pull only shows new
  items since last time, unless the user asks for "all time."
- View is presentable as-is for reading aloud/using as an agenda
  (plain list, chronological).
**Depends on:** FR-11 (needs MEETING-tagged data to exist to test
against, though technically could reuse existing historical data too).

### FR-13: Start-of-Day (SOD) nudge
**Description:** A nudge mirroring EOD's structure, firing near
`day_start`: readback of today's open `TODO`s (from FR-07's list) and
any relevant `GOAL`s, with a chance to add/adjust before the day
starts.
**Acceptance criteria:**
- SOD nudge fires once per workday near configured `day_start`.
- Shows today's carried-forward/open `TODO`s and current `GOAL`s.
- User can add a new `TODO`/`GOAL` directly from this nudge.
- Follows the same `fyne.Do` threading pattern as other scheduled
  UI-touching code (per AGENTS.md/session notes — scheduled callbacks
  run off the Fyne main thread).
**Depends on:** FR-07 (TODO list), FR-04 (scheduler already reworked
for interval-based nudges, good place to add SOD too).

### FR-14: Start-of-Month (SOM) wizard
**Description:** A multi-step monthly sequence (unifying "EOM review"
and "Start-of-Month wizard" per PRD §9): review last month's digest/
status report; review & cleanup `IDEA`/`SOMEDAY` entries (promote to
`TODO`/`GOAL` or drop); explicit prompts for `IMPACT`/`MILESTONE`
entries from the past month; set/revisit monthly-level `GOAL`s.
**Acceptance criteria:**
- Reachable from tray ("Start of Month..." or similar), and/or
  auto-fires once near the start of a new calendar month.
- Step 1 shows (or generates via existing Summarize pipeline) a
  digest of the prior month.
- Step 2 lists open `IDEA`/`SOMEDAY` lines from the prior month with a
  simple action to promote each to `TODO` or `GOAL`, or mark as
  dropped (append-only: dropping just means no further action, not
  deleting the original line).
- Step 3 explicitly asks "any IMPACT or MILESTONE items this month?"
  with quick-entry fields for each.
- Step 4 lets the user log/review `GOAL` lines for the new month.
- Each step's data writes clean ledger lines with correct categories.
**Depends on:** FR-03 (SOMEDAY/IMPACT/MILESTONE categories must exist
and be usable), FR-06 (legend helps users know what IMPACT/MILESTONE
mean when prompted), FR-11 territory not required.

### FR-15: Ad hoc mini-calendar for recurring meetings
**Description:** A minimal recurring-event list: name/tag, day-of-week,
time-of-day, one recurrence shape only (weekly). Powers pre-meeting
nudges.
**Acceptance criteria:**
- A form (Settings-adjacent or its own screen) to add/edit/delete
  recurring entries: tag, DOW, time.
- Config persisted under `DUNNIT_DIR` (new config section or file).
- No calendar/`.ics`/`EventKit` integration — purely user-entered.
**Depends on:** none structurally, but only useful once FR-16 exists.

### FR-16: Pre-meeting nudge (~15 min before) using mini-calendar
**Description:** ~15 minutes before a configured recurring meeting's
time, automatically surface relevant content: for a `#dsu`-tagged
entry, the standup-formatted export (FR-17); for other tags, the
accumulated `MEETING` agenda for that tag (FR-12).
**Acceptance criteria:**
- Scheduler checks configured recurring meetings (FR-15) and fires a
  nudge ~15 min prior.
- `#dsu`-tagged (or configurably-named) entries trigger the standup
  export view; other tags trigger the FR-12 agenda view for that tag.
- No nudge fires for a recurring entry with no upcoming occurrence
  today.
**Depends on:** FR-15, FR-12, FR-17.

## Phase 4 — Reporting, review, and reflection

### FR-17: Standup-formatted export (deterministic, no LLM)
**Description:** One-command export of yesterday's `DONE`/`WIN` lines
formatted as a short standup message — cheaper/faster than the full
`gh copilot` Summarize, no LLM call needed.
**Acceptance criteria:**
- Tray action ("Standup summary" or similar) produces a short,
  readable bullet list of yesterday's `DONE`/`WIN` lines, copied to
  clipboard and/or shown in a window.
- No network/LLM call involved; pure local ledger parsing.
**Depends on:** none.

### FR-18: Persistent, hand-editable daily summary doc
**Description:** Formalize the "two daily files" design: alongside
today's ledger, maintain a separate markdown summary doc (e.g.
`summary-<YYYYMMDD>.md`) that's LLM-drafted (reusing the Summarize/
`gh copilot` pipeline) then always hand-editable afterward, never
silently regenerated/overwritten.
**Acceptance criteria:**
- A new file `summary-<YYYYMMDD>.md` (or agreed naming) is created
  under the same date-partitioned directory as the ledger.
- An action (EOD-triggered or manual) drafts initial content into this
  file via the existing `gh copilot` pipeline, only if the file
  doesn't already exist (never overwrites existing hand-edited
  content).
- File opens in `$EDITOR` (or in-app) for review/editing, same pattern
  as ledger editing.
**Depends on:** none technically, but conceptually pairs with FR-13
(EOD flow) as the natural trigger point.

### FR-19: Weekly/monthly digest, proactively surfaced
**Description:** A digest nudge that appears on its own (not just
on-demand) — e.g. Friday afternoon for weekly, tied into SOM (FR-14)
for monthly.
**Acceptance criteria:**
- A scheduled nudge fires weekly (configurable day/time) showing a
  digest (reuse Summarize pipeline) of the past week.
- Monthly version is folded into FR-14's SOM wizard rather than a
  separate mechanism.
**Depends on:** FR-04 (scheduler rework), FR-14.

### FR-20: Sentiment/productivity trend view
**Description:** Visualize the EOD-captured 1-5 productivity score and
sentiment rating over time (crude sparkline or plain-text trend is
sufficient).
**Acceptance criteria:**
- A view (tray-accessible) shows a simple trend of productivity/
  sentiment scores over a selectable range (e.g. last 30 days).
- No new data capture needed — purely reads existing `PRODUCTIVITY`/
  `SENTIMENT` ledger lines.
**Depends on:** none (data already exists).

### FR-21: Search across ledger history
**Description:** Search by tag/category/keyword across all
`ledger-*.txt` files under `DUNNIT_DIR` without shelling out to `grep`
manually.
**Acceptance criteria:**
- A search field/action returns matching lines with file/date context,
  reasonably fast even across a year+ of ledgers.
**Depends on:** none.

### FR-22: Annual Review command
**Description:** Gather `IMPACT`/`MILESTONE` (and optionally `WIN`)
lines across a calendar year and summarize via the existing Summarize/
`gh copilot` pipeline with a performance-review-flavored prompt.
**Acceptance criteria:**
- New tray action, prompts for year (default: current), gathers
  matching lines from `$DUNNIT_DIR/<year>/**/ledger-*.txt`.
- Produces a narrative summary via the LLM pipeline, framed around
  accomplishments/impact rather than daily activity.
- Implemented as a variant of existing Summarize code (shared
  plumbing), not a parallel implementation, if at all reasonable.
**Depends on:** FR-03 (categories must exist to have been logged),
FR-14 (SOM prompting for these categories monthly improves the data
Annual Review has to work with, though not a hard code dependency).

### FR-23: Status-report export (dual audience)
**Description:** A date-range status report, with a "private" version
and a lightly-adaptable "shareable" version (for boss/colleagues),
likely a Summarize prompt/template variant.
**Acceptance criteria:**
- User picks a date range; gets a generated report with a clear
  private/shareable distinction (e.g. two prompt templates, or one
  report with a "share-safe" toggle that strips personal-only
  categories like `SENTIMENT`).
**Depends on:** none beyond existing Summarize plumbing.

### FR-36: Post-meeting quick-capture
**Decided: build it, early shape defined.** Micah: too early to know
a lot yet, but leaning toward this being a focused capture *session*
right after a meeting ends — a quick multi-category dump rather than a
single free-text note — likely covering `TIL`, `TODO`, `GOAL`,

**Acceptance criteria (draft, refine once used a few times in
practice):**
- Action reachable from tray (and/or auto-suggested by the pre-meeting

  passes) starts a short "post-meeting capture" session.
- Session presents quick-entry fields/prompts for at least `TIL`,
  `TODO`, `GOAL`, `RISK` categories (skippable — no field required),
  tag-scoped to the same meeting tag used for prep (e.g. `#boss`) so
  entries logically group with that meeting's `MEETING`-tagged prep
  notes.
- Each filled field writes its own correctly-categorized ledger line;
  skipped fields write nothing.
- Session is quick to dismiss/complete — no more friction than the
  existing EOD nudge's multi-field form.
- Revisit the exact category set after a few real uses — Micah
  explicitly expects this list may grow/change with experience.
**Depends on:** FR-11/FR-12 conceptually (shares the tag-scoping idea),
though not a hard code dependency.
